네. **Todo 웹앱을 처음부터 만드는 흐름이라면 `지침 생성 → 개발 → 검증`으로 시작하는 편이 훨씬 좋습니다.** Codex는 프로젝트의 `AGENTS.md`를 작업 전 지침으로 읽고, Claude Code도 `CLAUDE.md`를 프로젝트의 지속적 지침으로 사용하는 구조라서, 실제 CLI 에이전트 사용 방식과도 잘 맞습니다. ([OpenAI Developers][1])

그리고 이 방식의 장점은 뒤에서 설명할 **Prompt → Context → Harness → Loop**를 앞부분에서 이미 체험하게 만들 수 있다는 점입니다.

# PART 1을 이렇게 바꾸는 것을 추천합니다

## 「Todo 웹앱을 CLI 바이브 코딩으로 만들어보자」

발표에서는 처음부터 개념을 설명하지 않고 이런 상황으로 시작합니다.

```text
목표

간단한 Todo 웹앱 만들기

기능
- Todo 추가
- 완료 처리
- 삭제
- 완료 항목 숨기기
```

그리고 질문합니다.

> 보통 바이브 코딩을 처음 하면 어떻게 할까요?

```text
"Todo 웹앱 만들어줘"
```

그런데 바로 이렇게 시키지 않는다는 것이 이번 발표의 첫 번째 포인트입니다.

---

# 1단계. 프로젝트 지침부터 만든다

터미널에서 빈 프로젝트를 준비합니다.
우리는 이미 생성하였기 때문에 생략. 

CLI Agent를 실행하고 처음부터 코드를 만들게 하지 않습니다.

```text
Todo 웹앱 프로젝트를 시작하려고 해.

코드를 작성하기 전에
이 프로젝트에서 AI가 따라야 할 개발 지침을 먼저 만들어줘.

다음 내용을 포함해줘.

- 프로젝트 목적
- 사용할 기술 스택
- 기본 디렉터리 구조
- 코딩 원칙
- 작업 방식
- 테스트 방법
- 검증 명령
- 금지 사항
- 완료 조건

아직 애플리케이션 코드는 작성하지 마.
```

그리고 Codex라면:

```text
AGENTS.md
```

Claude Code라면:

```text
CLAUDE.md
```

같은 프로젝트 지침을 만듭니다. Codex 공식 문서도 `AGENTS.md`에 코드베이스 탐색 방법, 테스트 명령, 프로젝트 관행 등을 줄 수 있다고 설명하고 있고, Claude Code 역시 `CLAUDE.md`를 코딩 표준·워크플로·프로젝트 구조 같은 지속적 지침에 사용하도록 안내합니다. ([OpenAI Developers][1])

---

# 2단계. 만들어진 지침을 사람이 검토한다

여기서 **아주 중요한 장면**을 하나 넣으면 좋겠습니다.

AI가 이런 지침을 만들었다고 합시다.

```markdown
# Project

간단한 Todo 웹앱

## Tech Stack

- React
- TypeScript
- Vite

## Development Rules

- TypeScript strict mode 사용
- 컴포넌트는 작게 유지
- 관련 없는 리팩터링 금지
- 새로운 라이브러리는 필요할 때만 추가

## Workflow

작업 전:
1. 관련 코드 확인
2. 변경 계획 작성

작업 후:
1. 테스트
2. lint
3. build
4. git diff 확인

## Validation

npm test
npm run lint
npm run build

## Done

- 요청 기능 구현
- 테스트 통과
- lint 통과
- build 통과
- 불필요한 변경 없음
```

그다음 사람에게 보여줍니다.

```text
AI가 지침 생성
       ↓
사람이 검토
       ↓
프로젝트 규칙 확정
```

여기서 메시지는 이것입니다.

> **코드를 생성하기 전에 AI가 어떻게 일할지를 먼저 정한다.**

이건 이번 발표 전체를 관통하는 메시지와 정확히 맞습니다.

---

# 3단계. 이제 요구사항을 전달한다

그제야 실제 개발을 시작합니다.

```text
이제 Todo 웹앱을 만들어줘.

우선 기본 기능은

1. Todo 추가
2. Todo 목록 표시
3. 완료 상태 변경
4. Todo 삭제

야.

AGENTS.md의 프로젝트 지침을 따르고,
바로 구현하지 말고 먼저 구현 계획을 제시해줘.
```

그러면:

```text
요구사항
   ↓
프로젝트 지침
   ↓
Agent 계획
```

이 됩니다.

여기서 자연스럽게 보여줄 수 있습니다.

### 그냥 바이브 코딩

```text
Todo 만들어줘
     ↓
AI 마음대로 구현
```

### 관리되는 바이브 코딩

```text
목표
 ↓
프로젝트 지침
 ↓
계획
 ↓
구현
```

이 차이가 중요합니다.

---

# 4단계. 계획을 먼저 확인한다

예를 들어 AI가:

```text
1. Vite + React + TypeScript 구성
2. Todo 타입 정의
3. Todo 상태 관리
4. TodoInput 구현
5. TodoList 구현
6. TodoItem 구현
7. 테스트 작성
8. lint / build 실행
```

이라고 했다면,

발표자가 말합니다.

> 여기서 저는 아직 코드 한 줄도 작성하라고 하지 않았습니다.

그리고 계획이 괜찮으면:

```text
계획대로 진행해줘.

단,
우선 기본 Todo 기능까지만 구현하고
완료 항목 숨기기는 다음 작업으로 남겨줘.
```

이렇게 **작업 범위를 제한**합니다.

---

# 5단계. Agent가 실제로 개발한다

여기가 사람들이 생각하는 일반적인 바이브 코딩입니다.

```text
Agent
 │
 ├─ package.json 생성
 ├─ 프로젝트 초기화
 ├─ src 구성
 ├─ 컴포넌트 생성
 ├─ 상태 관리
 └─ 테스트 작성
```

하지만 발표에서는 코드 자체를 길게 보여주지 않는 편이 좋습니다.

오히려:

```text
AI가 파일을 읽고
→ 파일을 만들고
→ 명령어를 실행하고
→ 결과를 다시 판단한다
```

는 것을 보여줍니다.

즉 ChatGPT에 코드를 물어보는 것과 달리:

```text
LLM
 │
 ▼
Agent
 │
 ├── File
 ├── Shell
 ├── Git
 └── Test
```

가 된다는 것을 보여주는 겁니다.

---

# 6단계. 추가 기능을 바이브 코딩으로 넣는다

기본 Todo가 만들어졌으면 이제 실제 개발 같은 상황을 만듭니다.

> 기획자가 새로운 요구사항을 줬습니다.

```text
완료된 Todo를 숨길 수 있는 기능을 추가해주세요.
```

그런데 역시 바로:

```text
추가해줘
```

가 아니라:

```text
완료된 Todo를 숨기는 기능을 추가하려고 해.

먼저 현재 구현을 확인하고

- 수정해야 할 파일
- 기존 상태 관리 방식
- 가장 작은 변경 방법
- 필요한 테스트

를 정리해줘.

아직 수정하지 마.
```

라고 합니다.

이제 이전에 이야기했던:

```text
Explore
   ↓
Plan
   ↓
Implement
```

가 아주 자연스럽게 등장합니다.

**처음 프로젝트를 만들 때는 지침 생성부터, 이후 기능을 변경할 때는 탐색부터**인 겁니다.

---

# 7단계. 검증 Loop를 보여준다

그다음 기능을 구현시킵니다.

```text
계획대로 구현해줘.

구현 후에는 프로젝트 지침에 정의된
검증 명령을 모두 실행해줘.

실패하면 원인을 분석하고 수정한 뒤 다시 검증해줘.
```

그러면 화면상으로는:

```text
             구현
              │
              ▼
            Test
              │
          실패 ─ 성공
           │      │
           ▼      ▼
         분석    Lint
           │      │
           ▼   실패 ─ 성공
          수정    │      │
           │      ▼      ▼
           └──── Build
                  │
              실패 ─ 성공
               │      │
               └─수정─┘
```

이게 바로 나중에 설명할 **Loop**의 실물 예제가 됩니다.

---

# 8단계. 마지막은 AI Review + Human Review

검증까지 끝났다고 바로 완료하지 않습니다.

```text
현재 git diff를 검토해줘.

다음을 확인해줘.

- 요구사항이 모두 구현되었는가
- 불필요한 변경이 있는가
- 테스트가 누락되지 않았는가
- 복잡하게 구현한 부분은 없는가
- 프로젝트 지침을 위반한 부분이 있는가

문제가 있으면 수정하지 말고 먼저 알려줘.
```

그다음:

```bash
git status
git diff
```

를 사람이 봅니다.

최종 구조:

```text
AI Implementation
       ↓
Test / Lint / Build
       ↓
AI Review
       ↓
git diff
       ↓
Human Review
```

---

# 그러면 PART 1 전체가 하나의 이야기로 됩니다

저는 기존의

```text
Explore
→ Plan
→ Implement
→ Verify
→ Review
```

보다 발표에서는 **한 단계 앞을 추가하는 게 좋겠습니다.**

```text
┌──────────────────────────────┐
│ 1. Define                    │
│    프로젝트 지침 만들기       │
│    AGENTS.md / CLAUDE.md     │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ 2. Explore                   │
│    현재 프로젝트 이해         │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ 3. Plan                      │
│    구현 계획                  │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ 4. Implement                 │
│    작은 단위로 구현           │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ 5. Verify                    │
│    Test / Lint / Build       │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ 6. Review                    │
│    AI Review + Human Review  │
└──────────────────────────────┘
```

다만 **Define → Explore → Plan...을 새로운 업계 표준 용어처럼 설명할 필요는 없습니다.** 발표를 이해시키기 위한 우리의 작업 흐름으로만 사용하면 됩니다.

## 이 구성이 특히 좋은 이유

나중에 2번 파트로 넘어갔을 때 청중에게 이렇게 설명할 수 있습니다.

> 방금 Todo 앱을 만들면서 사실 우리는 네 가지를 이미 사용했습니다.

```text
"Todo 앱을 만들어줘"
        │
        ▼
Prompt Engineering
어떻게 요청했는가


AGENTS.md / CLAUDE.md
관련 코드 / 요구사항
        │
        ▼
Context Engineering
무엇을 알고 일했는가


지침 + Git + Test + Shell + 권한
        │
        ▼
Harness Engineering
어떤 환경에서 일했는가


구현 → 테스트 → 오류 → 수정 → 재검증
        │
        ▼
Loop Engineering
어떻게 반복하게 했는가
```

이렇게 하면 **PART 1에서 먼저 경험시키고, PART 2에서 방금 한 행동에 이름을 붙여주는 구조**가 됩니다.

저는 이 순서가 지금까지 잡은 발표 방향 중 가장 좋다고 봅니다. 특히 `AGENTS.md`부터 시작하면 발표의 핵심인 **“AI에게 코드를 많이 생성시키는 게 아니라, AI가 제대로 일할 수 있는 환경을 먼저 만든다”**가 Todo 예제 하나로 끝까지 유지됩니다.
